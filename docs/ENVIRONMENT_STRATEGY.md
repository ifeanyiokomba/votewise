# VoteWise — Environment Strategy

> Spec: "Separate environments completely. Production data must never be used in development."

VoteWise runs four fully-isolated environments. No environment shares data,
secrets, or infrastructure with another.

## Environment Matrix

| Environment | Purpose                          | Data        | Domain                        | Secrets Source          |
|-------------|----------------------------------|-------------|-------------------------------|-------------------------|
| Development | Local dev, hot reload            | Synthetic   | `localhost:3000`              | `.env` (gitignored)     |
| Testing     | CI / automated tests             | Synthetic   | `localhost:3000`              | `.env.testing.example`  |
| Staging     | Pre-prod validation, UAT         | Anonymised  | `staging.votewise.com.ng`     | AWS Secrets Manager     |
| Production  | Live elections, real voters      | Real        | `votewise.com.ng`             | AWS Secrets Manager     |

## Isolation Rules

1. **No data sharing.** Each environment has its own database (separate RDS
   instances). Production data is NEVER cloned into staging or development.
   Staging uses a synthetic voter register generated by the seed scripts.

2. **No secret sharing.** Each environment has its own set of secrets
   (encryption keys, peppers, HMAC secret). The production `VOTE_ENC_KEY`
   cannot decrypt staging ballots and vice versa. Secrets are stored in
   AWS Secrets Manager (production/staging) or `.env` files (dev/test,
   gitignored).

3. **No infrastructure sharing.** Each environment has its own VPC, RDS,
   ElastiCache, S3 bucket, and ECS cluster. The Terraform `environment`
   variable (`staging` | `production`) parameterises every resource name.

4. **DNS isolation.** Each environment has its own Route53 hosted zone:
   `staging.votewise.com.ng` and `votewise.com.ng`. No cross-environment
   DNS.

## Terraform Parity

Both staging and production are provisioned from the SAME Terraform module
(`infrastructure/main.tf`). Only the `tfvars` file differs:

```bash
# Staging
terraform apply -var-file=infrastructure/tfvars/staging.tfvars

# Production
terraform apply -var-file=infrastructure/tfvars/production.tfvars
```

The tfvars files set instance sizes, replica counts, Multi-AZ, and backup
retention per environment. See:
- `infrastructure/tfvars/staging.tfvars` — smaller instances, single NAT,
  7-day backups, `multi_az = false`.
- `infrastructure/tfvars/production.tfvars` — r6g instances, 3-AZ, 30-day
  backups, `multi_az = true`.

## Deployment Flow

```
Developer Push → Testing (CI) → Staging (auto) → Production (manual approval)
```

- **Push to `staging` branch** → CI runs → deploys to staging automatically.
- **Push to `main` branch** → CI runs → requires manual approval → deploys
  to production via blue-green (zero-downtime).
- **No direct production deployments.** See `.github/workflows/ci-cd.yml`.

## Data Retention

- Development: reset anytime (SQLite file).
- Testing: ephemeral (in-memory / temp file, discarded after each run).
- Staging: 7-day backup retention.
- Production: 30-day automated backups + monthly archives + cross-region
  replication to `eu-central-1` (Frankfurt).
